# Gemini 검수 — Kimi 가이드 흡수 (gemini-2.5-pro)

## AI 슬라이드 자동생성 엔진 평가 보고서

### 1. 사실검증: [C] 외부 조사 핵심 주장

*   **'3배' 레버리지**: **과장.** 슬라이드별 생성 품질 향상은 정량적 증명 없는 마케팅 수사이며, 자동화 파이프라인의 전체 일관성을 해칠 수 있음.
*   **'초기 입력 가중치'**: **사실 (경험적).** LLM의 주의 집중(attention) 메커니즘 상, 컨텍스트 시작 부분의 정보가 후속 생성에 더 큰 영향을 미치는 경향이 있음.
*   **'Kawasaki 10/20/30'**: **사실.** Guy Kawasaki가 제안한 유명 피치덱 프레임워크임. [C]는 그중 슬라이드 수(10개)만 언급함.
*   **'recency bias 시작+끝 반복'**: **사실.** 긴 컨텍스트에서 모델이 중간 내용을 간과하는 'lost in the middle' 현상을 완화하기 위한 알려진 프롬프트 기법임.

### 3. 델타 검증: 클차장 진단 및 추가 델타

클차장의 3개 델타 진단은 대체로 정확함. 단, 델타1의 가치는 과대평가되었으며, 자동화 파이프라인 관점에서 더 중요한 델타를 놓침.

*   **델타1 (슬라이드별 반복생성)**: 클차장의 평가는 **과대평가됨.** 자동화 파이프라인에서 N개 페이지에 N+1회 LLM 호출은 비용과 지연시간을 급증시키고, [A]의 핵심인 '지배 메시지' 기반의 덱 전체 논리 일관성을 파괴할 위험이 큼. '최대 레버' 주장은 근거 없음.
*   **델타2 (Few-shot 골드예시)**: **유효함.** [B]의 프롬프트는 규칙 나열에 그침. LLM은 예시를 통해 출력 포맷과 톤을 훨씬 효과적으로 학습하므로, 이는 즉각적인 품질 개선을 가져올 수 있음.
*   **델타3 (프롬프트 역학)**: **유효함.** 자동 래퍼에서 지시 반복, 구분자, 출력 프라이밍을 적용하는 것은 프롬프트 안정성을 높이는 표준적 구현 디테일임.

#### 클차장이 놓친 진짜 델타 (자동화 파이프라인 관점)

1.  **적대적 검증 단계 (Adversarial Review Pass)**: [C]의 '적대적 투자자 재작성'은 단순 약점 노출([A] 원칙 8)을 넘어선 개념. 생성된 `deck_blueprint.json`의 논리를 비판하는 별도의 "비판가" LLM 호출 단계를 파이프라인에 추가할 수 있음. 이는 자동화 가능하며 논리적 견고성을 크게 향상시키는 핵심 델타임.
2.  **청중 페르소나 기반 동적 톤 조절 (Dynamic Toning by Audience Persona)**: [C]의 '청중 먼저' 원칙을 틱덱은 필드(`audience`)만 받고 활용은 못 하고 있음. [A]의 톤은 '컨설팅+후추님'으로 고정됨. `audience` 값('경영진', '개발자', '신입사원')에 따라 어휘 수준, 전문성, 강조점을 동적으로 조절하도록 ③페이지 구성 프롬프트에 명시적 지시를 추가해야 함.
3.  **다중 논리 골격 라우팅 (Multi-Framework Routing)**: 틱덱은 현재 [A]의 "사업화형" 단일 골격에 고정됨. 입력 리포트의 유형(시장 분석, 기술 리뷰, 연대기)을 초기에 판단하고, 그에 맞는 최적의 스토리 아크 템플릿([A] 스토리 아크 옵션 등)을 선택적으로 적용하는 로직이 없음.

### 4. 흡수 우선순위 제안 (임팩트×난이도)

1.  **Few-shot 예시 추가 (임팩트: 상, 난이도: 하)**
    *   **무엇을**: 모범적인 `page_specs.json`의 페이지 객체 2~3개를 '골든 예시'로 제작.
    *   **어디에**: [B] 문서의 §3 '③ 프롬프트 법칙'에 추가하고, 실제 작가 LLM 시스템 프롬프트에 포함.
    *   **왜**: 규칙만 나열하는 것보다 LLM이 원하는 출력 형식과 톤을 가장 빠르고 정확하게 학습하게 함. 즉시적인 품질 향상 기대.

2.  **적대적 검증 단계 도입 (임팩트: 최상, 난이도: 중)**
    *   **무엇을**: ②단계에서 생성된 `deck_blueprint.json`을 입력받아 논리적 약점, 근거 부족, 성급한 일반화를 지적하는 "비판가" LLM 호출 단계를 신설. 작가 LLM은 이 피드백을 반영해 blueprint를 수정함.
    *   **어디에**: [B] '정본 FLOW'의 ②와 ③ 사이에 `②-2. 비판 및 수정` 단계를 명시하고, `deck_author.py`에 해당 로직을 구현.
    *   **왜**: 생성된 덱의 논리적 취약점을 시스템 스스로 보완하게 하여 설득력을 근본적으로 강화함. 클차장이 놓친 가장 큰 델타.

3.  **청중 기반 동적 톤 조절 (임팩트: 상, 난이도: 중)**
    *   **무엇을**: `deck_blueprint.json`의 `audience` 필드 값을 ③단계 프롬프트의 핵심 제약 조건으로 사용. "청중이 [X]이므로, 전문 용어 사용 수준을 [Y]로 조절하고, [Z] 관점을 강조하라"는 동적 지시를 추가.
    *   **어디에**: [B] 문서의 §3 '③ 프롬프트 법칙'에 해당 지침을 추가하고 프롬프트 템플릿에 반영.
    *   **왜**: 현재 고정된 톤에서 벗어나 실제 사용 맥락에 맞는 맞춤형 덱을 생성하여 효용성을 크게 높임.

4.  **프롬프트 래퍼 고도화 (임팩트: 중, 난이도: 하)**
    *   **무엇을**: 중요 지시사항(예: "JSON 형식만 출력")을 프롬프트 시작과 끝에 반복하고, 명확한 구분자(`---`)를 사용하며, JSON 출력 시작을 유도하는 프라이밍(`{"topic":`)을 적용.
    *   **어디에**: LLM 호출을 감싸는 래퍼 함수(`anthropic_call_wrapper.py`)에 구현.
    *   **왜**: LLM의 출력 안정성을 높이고 형식 오류를 줄이는 기본적인 엔지니어링 개선임.
